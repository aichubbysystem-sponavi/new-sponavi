==========================================================
2026-08-08 GBP店名変更への追従 / 店舗インポートの不具合修正
==========================================================

■ 発端
「ジェルネイル専門 WHITE NAIL 高崎店」を顧客マスタで検索しても0件になる。
GBPの権限は chubby.co.ltd.1204 / chubby1204.meo / meo@japanselect の3つで持っている。

■ 調査結果（実データで確認）
権限の問題ではなかった。この店舗は既に登録されている。

  locations/2042073457397401125
  shop_id 5c39acb6-3e8b-45aa-96ac-0f9fa6a1e35c
  DB name : アイブロウサロンWHITE EYE まつ毛と眉毛の専門店 高崎店 ホワイトアイ
  GBP title: ジェルネイル専門 WHITE NAIL 高崎店   （GBP APIで直接確認。カテゴリ=ネイルサロン、027-386-2655）

アイブロウ店→ネイル店に業態変更してGBP名だけ変わり、SPOTLIGHT側が追従していなかった。

0件になる理由は2段階:
 1) インポートは gbp_location_name（ロケーションID）で既存判定してスキップし、名前を更新しない
    （gbp-accounts/page.tsx の事前判定、cron/sync-shops も gbp_full_path とカテゴリのみ書き戻し）
 2) 顧客マスタの検索 fuzzyMatch は入力の全単語がDB名に含まれることを要求する
    → 「ジェルネイル専門」がDB名に無いので0件

■ 同時に判明した問題
 (a) 名前ズレが28件（DB名 ≠ GBP現在名）
 (b) 2026-08-08に追加された3件（うら山本店 / shisha cafe&bar 煙工房 / 鍼灸整体院 ENISHI）は
     gbp_location_name が NULL。Go APIの POST /api/shop が gbp_location_name を保存していない
 (c) cron/sync-shops は accounts.slice(0,5) で先頭5アカウントしか見ていない。
     実際は9アカウント見えている（4アカウントが恒常的にスキャン対象外）
 (d) 同一GBPロケーションに店舗が2行ある重複が5件
     ニュークラブ NOBLE / Four Seasons / SEASIDE CLUB / Red Shoes / 熱塩温泉 山形屋
 (e) lib/gbp-location.ts の GBP APIフォールバック4箇所が Authorization: `Bearer ` （トークン変数が抜けていた）
     → フォールバック経路は常に401だった
 (f) system_oauth_tokens は LIMIT 1 のVIEWなので実質1トークン。
     /api/google/token が返すのは chubby.yamada@gmail.com のトークンのみ
     （他4アカウントのトークンは 2026-06-23 以降リフレッシュされていない）

■ 設計判断: shops.name は絶対に自動更新しない
shops.name は「システム全体の結合キー」であり、以下が全て文字列一致で紐付いている。
  reviews.shop_name / report_analysis.shop_name / pmax_*.shop_name /
  grid_ranking_logs.shop_name / report_display_settings.shop_id /
  user_shop_access.shop_name / 投稿用スプレッドシートのB列 / Dropbox写真フォルダ名
name を GBP名で上書きすると過去データが行方不明になり、自動投稿は
auto-post の「店舗未登録（スキップ）」で静かに止まる。

→ GBP上の現在名は gbp_shop_name に同期し、name はそのまま。
   auto-post は既に name / gbp_shop_name の両方で照合しているため、
   旧名のままのシートも、新名に直したシートも、どちらも通る（別名として機能する）。

追記: セルフレビューで見つかった問題と修正（同日）

■ 高1: 「ロケーション解除」が毎晩自動で取り消される問題
  gbp-shop-sync の link分岐が「gbp_location_name が空 + 名前がGBPタイトルと一致」で
  自動再紐付けするため、担当者が意図的に外した連携をcronが復活させてしまう。
  （現時点の該当は0件。NULL 50件のうち名前一致は復活させたい3件だけ。構造的な欠陥）
  修正:
   - syncShopsFromGbp に autoLink オプション追加。
     手動実行(/api/report/gbp-sync POST)のみ true。cronは false で候補報告(linkable)のみ。
   - 新規 POST /api/report/shop-unlink … 解除したロケーションIDを
     previous_gbp_location_name に残す（このカラムは未使用だった。0行）。
     同期側は previous_gbp_location_name があれば自動紐付けせず conflict 報告に回す。
   - customer-master の handleUnlinkGbp を Go API PUT から新ルートへ変更。

■ 高2: スキャンが部分的に失敗しても「エラー0・完了」に見える問題
  listLocations の 401/403 は skipped=true を返すだけで errors に積んでいなかった。
  「別トークンで再試行される」前提だが実運用の有効トークンは1本なので再試行されない。
  アクセストークンは1時間で切れるため、スキャン中の期限切れで実際に起こりうる。
  （検証中も同条件で 517件取れた回と 453件しか取れなかった回があった）
  さらに scanAllGbpLocations 末尾に「スキャンできなかったアカウントを明示する」という
  コメントだけがあり、実装が無かった。
  修正: 全トークン試行後、seenAccounts にあって scannedAccounts に無いアカウントを
        必ず errors に積む（「この配下は今回同期されていません」）。

■ 中1: 店名変更の検出数とUIバッジ数が食い違う
  同期側=NFC完全一致で28件、UI側=NFKC+空白除去+小文字化。3件が同一扱いになりバッジが出ない。
   生ラムジンギスカン 新なるぼんず→新なるぼんず（空白）
   IHOKUBASE|伊北ベース→｜（全角半角）
   鮨 赫 sushi AKA Tokyo→Sushi（大文字小文字）
  修正: lib/normalize.ts に normShopName / isSameShopName を追加して両者で共有。
        検出は25件に揃った（gbp_shop_name に入れる値はGBP原文のまま）。

■ 中2: shop_name_changes 未作成のまま同期すると履歴が永久に取れない
  recordRenames はログを出すだけで続行していたが、gbp_shop_name を先に更新するため
  次回以降は差分が消えて二度と検出できない。
  修正: 履歴の記録を「gbp_shop_name の更新より前」に移動。
        記録に失敗したら該当行の gbp_shop_name 更新だけ取り下げて次回に持ち越す。
        エラー文にSQLファイル名を明示。

■ 中3: 複数アカウントに見えるロケーションで gbp_full_path がブレる + 安全ガードが無効化される
  locations/11708453413660533120（株式会社Chubby）と
  locations/15877184882855301460（SIK eatery うつぼ公園店）は
  「株式会社Chubby山田」(PERSONAL) と「Spotlight Navigator」の両方に出る。
  first-winsなのでGoogleのaccounts.list順に依存し、個人アカウントのパスが入ると
  knownAccounts に個人アカウントが登録されて新規取り込みの安全ガードが無効化される。
  修正: sortAccounts() で PERSONAL を後回し + name順に固定。
        結果 gbp_full_path の書き換えは5件→3件（いずれも 株式会社Chubby 03/05 の正当なパス）。
        個人アカウントは knownAccounts に入らないままになった。

■ 低: ページネーション上限 MAX_PAGES=100 を追加（同じpageTokenが返り続けた場合の無限ループ防止）
■ 低: クライアントtimeout 290秒 < サーバmaxDuration 300秒 だったので 320秒へ。
      ECONNABORTED時は「失敗」と断定せず再読込を促す文言に変更。
