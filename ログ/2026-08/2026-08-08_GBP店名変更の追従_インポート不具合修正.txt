■ 発端
「ジェルネイル専門 WHITE NAIL 高崎店」を顧客マスタで検索しても0件になる。
GBPの権限は chubby.co.ltd.1204 / chubby1204.meo / meo@japanselect の3つで持っている。

■ 調査結果（実データで確認）
権限の問題ではなかった。この店舗は既に登録されている。

  locations/2042073457397401125
  shop_id 5c39acb6-3e8b-45aa-96ac-0f9fa6a1e35c
  DB name : アイブロウサロンWHITE EYE まつ毛と眉毛の専門店 高崎店 ホワイトアイ
  GBP title: ジェルネイル専門 WHITE NAIL 高崎店   （GBP APIで直接確認。カテゴリ=ネイルサロン、027-386-2655）

アイブロウ店→ネイル店に業態変更してGBP名だけ変わり、SPOTLIGHT側が追従していなかった。

0件になる理由は2段階:
 1) インポートは gbp_location_name（ロケーションID）で既存判定してスキップし、名前を更新しない
    （gbp-accounts/page.tsx の事前判定、cron/sync-shops も gbp_full_path とカテゴリのみ書き戻し）
 2) 顧客マスタの検索 fuzzyMatch は入力の全単語がDB名に含まれることを要求する
    → 「ジェルネイル専門」がDB名に無いので0件

■ 同時に判明した問題
 (a) 名前ズレが28件（DB名 ≠ GBP現在名）
 (b) 2026-08-08に追加された3件（うら山本店 / shisha cafe&bar 煙工房 / 鍼灸整体院 ENISHI）は
     gbp_location_name が NULL。Go APIの POST /api/shop が gbp_location_name を保存していない
 (c) cron/sync-shops は accounts.slice(0,5) で先頭5アカウントしか見ていない。
     実際は9アカウント見えている（4アカウントが恒常的にスキャン対象外）
 (d) 同一GBPロケーションに店舗が2行ある重複が5件
     ニュークラブ NOBLE / Four Seasons / SEASIDE CLUB / Red Shoes / 熱塩温泉 山形屋
 (e) lib/gbp-location.ts の GBP APIフォールバック4箇所が Authorization: `Bearer ` （トークン変数が抜けていた）
     → フォールバック経路は常に401だった
 (f) system_oauth_tokens は LIMIT 1 のVIEWなので実質1トークン。
     /api/google/token が返すのは chubby.yamada@gmail.com のトークンのみ
     （他4アカウントのトークンは 2026-06-23 以降リフレッシュされていない）

■ 設計判断: shops.name は絶対に自動更新しない
shops.name は「システム全体の結合キー」であり、以下が全て文字列一致で紐付いている。
  reviews.shop_name / report_analysis.shop_name / pmax_*.shop_name /
  grid_ranking_logs.shop_name / report_display_settings.shop_id /
  user_shop_access.shop_name / 投稿用スプレッドシートのB列 / Dropbox写真フォルダ名
name を GBP名で上書きすると過去データが行方不明になり、自動投稿は
auto-post の「店舗未登録（スキップ）」で静かに止まる。

→ GBP上の現在名は gbp_shop_name に同期し、name はそのまま。
   auto-post は既に name / gbp_shop_name の両方で照合しているため、
   旧名のままのシートも、新名に直したシートも、どちらも通る（別名として機能する）。

追記3: 新規登録が全滅していたバグ（owner_id）
==========================================================

■ 症状
  一括登録ガードの一覧(169件)で「169件をすべて登録する」を押しても
  新規追加0件・要確認274件になり、DBは611件のまま増えなかった。
  274 = 前回の要確認105 + 追加失敗169。

■ 原因
  shops テーブルに owner_id カラムが存在しない。
  lib/gbp-shop-sync.ts の INSERT が owner_id を渡していたため、
  169件すべてが column "owner_id" of relation "shops" does not exist で失敗し、
  conflicts に「追加失敗: ...」として積まれていた。
  （UIは先頭20件しか出さないので、画面には前回と同じMEO用Chubbyの行だけが見えていた）

  オーナーは shops.business_group_id → business_groups.owner_id で解決される。
  Go APIの GET /api/shop が owner_id を返すのは結合結果であって、列ではない。
  最初にカラム一覧を取得していたのに突き合わせず、Go APIのレスポンスだけを見て
  列が存在すると思い込んだのが原因。CLAUDE.md「実データを必ず確認」の違反。

■ 検証方法（今後もこれをやる）
  本番DBに BEGIN → INSERT → ROLLBACK でテスト行を入れて再現・確認した。
  さらにコードのINSERT/UPDATE列名を information_schema.columns と突き合わせて
  存在しない列がゼロであることを確認した。

■ 修正
  - lib/gbp-shop-sync.ts: INSERTから owner_id を削除。business_group_id のみ渡す。
    事前チェックも「オーナー未登録」から「business_groups未登録」に変更
  - cron/sync-shops Step2 の insertRow からも owner_id を削除（同じ地雷が残っていた）

■ 教訓（重要ナレッジにも記載）
  Go APIのレスポンス項目 ≠ shops のカラム。書き込む前に必ず
  information_schema.columns と突き合わせること。
  owner_id / full_address / owner / group はGo API側の結合結果。

- shops.name は「システム全体の結合キー」として不変にする。GBP側の改名には追従しない。

### 注意点・ハマったこと
■ shops に owner_id カラムが無い ← 今回最大のミス
  Go APIの GET /api/shop は owner_id / full_address / owner / group を返すが、これらは
  結合結果であって列ではない。INSERTに渡すと
  column "owner_id" of relation "shops" does not exist で全件失敗する。
  カラム一覧を取得済みだったのに突き合わせず、APIレスポンスだけを見て存在すると思い込んだ。
  → shops に書き込むコードを足したら必ず information_schema.columns と照合する。
     本番検証は BEGIN → INSERT → ROLLBACK が安全で確実。

■ 失敗が画面に出ない構造だった
  169件のINSERT失敗は conflicts に「追加失敗: 〜」として積まれたが、UIは先頭20件しか出さず、
  その20件が前回と同じ内容だったため「要確認274件」の中に完全に埋もれた。
  数字（274 = 105 + 169）で気づけた。件数の内訳が合うかを必ず確認すること。

■ POSTでのデプロイ判定は不可能
  middleware のCSRFチェックは存在しないパスへのPOSTにも403を返す。
  デプロイ確認はGET（401なら存在／404なら未配備）か、
  ページのJSバンドルを取得して新しい文字列が含まれるかで判定する。

■ ローカルのドライランは「下限」であって正解ではない
  ローカルは Go APIの /api/google/token（chubby.yamada 1本）しか使えず 9アカウント/517ロケーション。
  本番は getAllOAuthTokens() が全トークンを更新するため 15アカウント/835ロケーション。
  ローカル検証で「0件」でも本番では大量に出うる。

■ 「ロケーション解除」が自動で戻る構造だった
  名前一致による自動紐付けが、担当者が意図的に外した連携を毎晩復活させる設計になっていた。
  現時点の該当は0件だが構造的欠陥。previous_gbp_location_name に印を残す方式で解消。

■ link分岐が knownAccounts チェックより前にあった
  レビューで気づきながら「影響は小さい」と判断して残した結果、本番で紐付け29件により
  未知アカウントが「既知」に昇格し、その配下169件が承認なしで登録される状態になった。
  → アカウント単位の判定に頼らず、件数でガードする構造側の対策に変更した。

■ 検出数とUIバッジ数の基準がズレていた
  同期側はNFC完全一致、UI側はNFKC+空白除去+小文字化。表記ゆれ3件がバッジに出なかった。
  lib/normalize.ts の isSameShopName を両者で共有して解消。

■ 履歴は gbp_shop_name の更新より先に書く
  後に書くと、記録に失敗した時点で差分が消えて二度と検出できない。
  順序を入れ替え、記録に失敗したら該当行の店名同期を次回に持ち越すようにした。

■ 課金の所在
  自動実行6本のうち課金するのは monthly-analysis のみ（Anthropic Haiku 4.5、$1/$5 per MTok）。
  Maps Platform / Google Ads を叩くcronは無い（座標一括取得・place-id補完・P-MAX同期は手動ボタン）。
  今回のコードは Anthropic も Maps も一切呼ばない。新規店舗の緯度経度はGBPの latlng から無料で取得。
