## 照合ポリシー（誤チェック事故を防ぐため段階を分けた）
1. 完全一致（NFKC + 小文字化 + 空白除去）        → 自動チェック
2. 記号無視の完全一致（括弧・中黒等を除去）      → 自動チェック
3. 1/2で候補が複数（同名店舗）                   → 自動チェックせず「要確認」
4. 一致なし                                      → 「未検出」。類似候補は提示するが自動チェックしない
※ 部分一致では絶対に自動チェックしない。
   実データ確認: 370店舗中3件（'CHILLRI' 等）が他店舗名の部分文字列になっており、
   部分一致で自動チェックすると別店舗を巻き込む。

## 実データでの精度検証

また同リスト370件について

  - 記号除去後の名前重複: 0件
→ 現状のデータでは1〜2の段階だけで一意に決まる。3の分岐は保険。

## UI仕様
- テキストエリアに複数行貼り付け → その場で自動照合（onPasteで実行）
- Enter = 照合実行 / Shift+Enter = 改行（IME変換中のEnterは無視）
- 既定は「置き換え」（貼り付けた店舗だけが選択される）。
  チェックボックス「既存の選択に追加する」で追加モードに変更可
- 結果を 一致N件 / 要確認N件 / 未検出N件 / 重複行N件 でバッジ表示
- 未検出・要確認はボタンで1件ずつ手動チェック可（「もしかして」候補付き）
- 行頭の「・」「1.」「- 」等、全角空白、空行、重複行は自動で処理

## 症状
20店舗を選んだ状態でプレビューを押すと
「エラー: timeout of 60000ms exceeded」（写真投稿・第2回目）。

## 調査（貼り付け機能の変更が原因ではない）
貼り付け機能側の変更は filterShopNames の要素が20→21に増えるだけで処理時間に効かない。
プレビュー(dryRun)はDropbox検索をスキップするので、重いのはシート読み取りだけ。
実際の待ち時間の内訳:
  1) getOAuthToken()  … Go API /api/google/token が20秒タイムアウト、
                        失敗するとDBリフレッシュで更に15秒 → 最悪35秒
  2) 3タブのCSV取得   … 直列。しかも fetch にタイムアウトが無かった
                        （Googleが応答しないとサーバーは maxDuration=300 まで待つ）
  3) 0件だった場合    … デバッグ情報のために同じ3タブをもう一度直列で取り直していた
クライアント側は60秒で諦めるため、サーバーがまだ処理中でも「timeout」と表示される。
つまり以前から起こりうる状態で、今回20店舗指定で表面化した。

## 修正（auto-post/route.ts）
- fetchSheetCsv() に切り出し、AbortSignal.timeout(25000) と cache:"no-store" を付与
  （no-store が無いとNext.js 14がシートのCSVをキャッシュしうる。既存の罠）
- 3タブのCSV取得を Promise.all で並列化。
  ただし行の処理はタブ順のまま（写真投稿の「同一店舗は最初の1行のみ」がタブ順依存のため、
  取得だけ並列にして処理順は変えない）
- 0件時のデバッグは取得済みCSVを使い回す（再取得をやめた）

## 修正（posts/page.tsx）
- プレビュー / 実行前プレビュー / 予約前プレビューの3箇所のクライアントtimeoutを 60秒→120秒
  （サーバーの maxDuration は300秒なので、クライアントが先に諦める構図を解消）
- タイムアウト時のメッセージを

    もう一度プレビューを押してください」に変更。

追記4: scheduled_posts.approval_status カラムが本番に存在しない
==========================================================

## 症状
予約投稿の「差戻し」を押すと
  変更失敗: Could not find the 'approval_status' column of 'scheduled_posts' in the schema cache

## 原因
コードは approval_status 前提だが、本番DBにカラムが無い（sql/ にも作成用SQLが無い）。
影響範囲は差戻しだけではない:
  - 承認（approval_status='approved'）… 失敗
  - 差戻し（approval_status='rejected'）… 失敗
  - 保留中の投稿の解除 / エラー投稿の再実行 … 失敗
    （scheduled-posts/route.ts:140-143 が status='pending' のとき
      approval_status='pending' も必ず一緒に更新するため）
  - cron/execute-posts:215 の filter(p => p.approval_status !== "rejected") は
    カラムが無いと常に true。つまり承認フローは最初から一切機能していない。
    予約は status='pending' かつ scheduled_at<=now なら5分おきに公開される。

## 対応
[新規] sql/2026-08-15_add_scheduled_posts_approval_status.sql
  ALTER TABLE scheduled_posts ADD COLUMN IF NOT EXISTS approval_status text;
  → 本番SQL Editorでの実行が必要（未実行のうちは承認・差戻し・保留解除が失敗し続ける）

## 誤登録分の停止方法（approval_status に依存しない手段）
  delete from scheduled_posts
  where status in ('pending','on_hold')
    and scheduled_at >= '2026-08-15T03:00:00Z';   -- 12:00 JST
  ※ status='rejected' への UPDATE は approval_status を触らなければ通るが、
    画面の「差戻し」ボタンは両方を同時に更新するため、カラム追加までは使えない。

## 追記4の実行結果（本番）
1) SELECT で残存を確認 → 6件のみ、すべて status='on_hold'
   （一文字premium / 西口酒場ホームラン、03:00〜03:02 UTC = 12:00〜12:02 JST）
   → status='pending' の行は既に無かった。つまり予約41件は12:00の cron で公開済み。
2) ALTER TABLE scheduled_posts ADD COLUMN IF NOT EXISTS approval_status text; → Success
   （承認 / 差戻し / 保留解除 / エラー再実行 が使えるようになった）
3) DELETE（pending/on_hold かつ scheduled_at>=12:00 JST）→ Success。残り6件を削除。

## 残作業
- 12:00に公開された分のうち、意図しない店舗のGBP投稿を削除する
  対象の洗い出しSQL:
    select shop_name, count(*) 件数, min(published_at) 最初, max(published_at) 最後
    from scheduled_posts
    where status='published' and scheduled_at >= '2026-08-15T03:00:00Z'

  写真エラー(400) 1件（一文字premium、Request contains an invalid argument）
  写真なし（スキップ）3件（メンズ眉毛サロン bloom 梅田 / 人類みな麺類 東京本店 /
                          LUXBE PREMIUM 大阪駅前第3ビル店）

## 原因（実データで確認）
  select name, gbp_location_name, gbp_full_path from shops where name in (...);
  一文字premium      accounts/111148362910776147900/locations/10299686485529233275
  西口酒場ホームラン accounts/111031567193825395772/locations/13235752382829797953
→ 別アカウント。auto-post の即時実行は getOAuthToken() の1本しか使っておらず

  cron/execute-posts は Go APIの店舗別トークン → 全トークン順次リトライ
  (execute-posts:258-274) なので通る。
  「予約なら投稿できるのに実行ボタンだと404」という差になっていた。

## 修正
[修正] auto-post/route.ts
  gbpFetchWithTokenFallback() を追加。
  401/403/404 のときだけ getAllOAuthTokens() の他トークンで順に再試行する。
  400などトークンと無関係なエラーは即打ち切り（再試行しても同じ）。
  401/403/404 は「作成されていない」ことが確定しているので二重投稿にはならない。
  トークン一覧はリクエスト単位でキャッシュ（cachedFallbackTokens、先頭でリセット）。
  適用箇所: 写真のみmedia POST / 本文空のmedia POST / localPosts POST(写真なし再試行含む) /
           投稿確認GET（別トークンで作られた投稿は既定トークンのGETが404になるため）

## 400と「写真なし」は別問題

  写真なし: Dropboxおおもとフォルダ221件に店舗名一致のフォルダが無い。
           フォルダ名を店舗名に合わせるか、シートF列に直接URLを入れる。システム側では解決不能。

追記6: 投稿できても写真が「表示できません」になる（同じトークン問題）

## 症状

- 401/403/404 のときだけ getAllOAuthTokens() の他トークンで再試行
- 成功したトークンは「ロケーション単位」で30分キャッシュ（locTokenCache）。
  同じロケーションの2枚目以降は総当たりしない

追記7: 写真投稿が削除できない（0件削除しました）

## 症状

  安全チェック（許可文字・パストラバーサル・ルート形式）を isSafeGbpResourceName に切り出し、
  isValidGbpMediaName（/media/ 必須）と
  isValidGbpDeletableName（localPosts または media）を追加。
  isValidGbpPostName の挙動は変えない（既存テストはそのまま通る）。
[修正] delete-post/route.ts
  - isValidGbpDeletableName を使用。ロケーション解決も /media/ 形式に対応
  - 401/403/404 は他トークンで再試行してから判断（追記5・6と同じアカウント問題。
    404を「既に削除済み」と即断すると、見えないだけの投稿を消したことにしてしまう）
  - 失敗理由を gbpError として返す（success:true だけ返して画面が「削除しました」と
    出るのに実際は残る、を防ぐ）
[修正] posts/page.tsx handleDelete

追記8: 動画（MOV/MP4）も投稿できるようにした
==========================================================

## 発端

Dropboxの「写真投稿26-8-2」は3ファイルあったが、
  写真投稿26-8-2 (1).png  → 投稿された
  写真投稿26-8-2 (1).MOV  → 拡張子フィルタで除外
  写真投稿26-8-2 (2).MOV  → 同上
auto-post の拡張子フィルタが jpg|jpeg|png|gif|webp|bmp だけだったため。
ユーザー判断で「動画も投稿する運用にする」ことになった。

## 実行パスの確認（触る前に全部たどった）
  即時実行  : auto-post → Dropbox検索 → image-proxy(安定URL化) → GBP Media API
  予約登録  : auto-post → Dropbox検索 → image-proxy → scheduled_posts.photo_url に保存
  予約実行  : cron/execute-posts → Go API media_direct → 失敗時 直接Media API
  表示      : post_logs.media_url → media-urls で取り直し → <img>

## 設計判断: DBカラムは増やさず、URLの拡張子で判定する
scheduled_posts に media_format を足す案もあったが、予約時に image-proxy が
Supabase Storage へ拡張子付きで保存している（sched-xxx.mp4 等）ため、
実行時にURLから判定できる。マイグレーション不要で経路が1つ減る。
※そのため image-proxy が拡張子を落とさないことが前提条件になった（下記）。

追記9: 「該当する投稿がありません」の原因が画面から追えない
==========================================================

## 症状
一文字premium を1店舗だけ選んで実行 → 「エラー: 2026-08-02に該当する投稿がありません」。
同じ店舗は今日の40店舗実行では3件マッチしていた。

## 分かっていること
写真投稿(isPhotoOnly)はE列日付を見ずB列店舗名だけで拾う。
つまり matches=0 は「B列にその店舗名の行が無い」＝店舗名の食い違い。
  - 40店舗実行時の結果に出ていた「一文字premium」は match.shopName＝シートB列の値
  - 再実行時に成功していたのは autoPostFailedShops（＝シートB列の値）で絞ったから
  - 今回は postTargetShopIds → shops.name（＋gbp_shop_name）で絞っている
→ shops.name とシートB列の表記が違う可能性が高いが、画面に絞り込み条件が
  出ていないため確定できなかった。

## 対応（原因を画面から追えるようにする）
サーバーは0件時に debug{ filterShopNames, tabResults(各タブ先頭5行のB列) } を返していたが、
クライアントはこれを捨てて「該当する投稿がありません」としか出していなかった。
[修正] posts/page.tsx
  - 実行・予約登録の0件時に zeroDebug としてサーバーのdebugを保持
  - プレビューも0件ならエラー表示に寄せる（従来は「プレビュー: 0件マッチ」で終わり）
  - 「0件だった理由を確認する」を開くと
      絞り込みに使った店舗名（この表記でシートB列と完全一致する必要があります）
      シート各タブの先頭5行のB列
    が並ぶ
